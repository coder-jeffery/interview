# Redis

> 面试权重：必会  
> 适合层级：所有人（中高级挖持久化、集群、锁、大 key）

## Q1: 为什么 Redis 快？单线程是不是绝对的？

**30 秒答法**  
内存 + IO 多路复用 + 高效数据结构 + 操作简单。所谓单线程指**命令执行**在主线程串行，避免锁。6.0 后 IO 线程可用来读解析/写回，但执行仍在主线程。CPU 不是永远够用：大 key、复杂度高的命令（`KEYS`、无限制 `SMEMBERS`、跨 slot 操作）会卡住所有请求。

**追问**  
- 持久化、过期、集群转发会不会用到别的线程？（会。AOF rewrite、RDB fork 子进程）  
- 为什么不把执行也做成多线程？（数据竞争、实现复杂；要吞吐用集群分片）

## Q2: 常见数据结构及编码（面试加分）

**30 秒答法**

| 类型 | 典型场景 | 别忽略的点 |
|------|----------|------------|
| String | 缓存对象、计数、分布式锁 value | 大 JSON 要考虑压缩与拆分 |
| Hash | 对象字段、购物车 | 小 hash 用 ziplist/listpack，避免全量 `HGETALL` 大对象 |
| List | 队列、最新 N 条 | 不要当可靠 MQ |
| Set | 去重、标签 | 交集注意大小 |
| ZSet | 排行榜、延迟队列 | skiplist + dict |
| Bitmap | 签到、布隆粗筛 | 偏移量别太大 |
| HyperLogLog | UV 近似 | 误差约 0.81%，不能取出元素 |
| Stream | 消息、消费组 | 可比 List 当简易 MQ，仍不是 Kafka |
| GEO | 附近的人 | 底层 zset |

**追问**  
- 延迟队列用 zset 的 score 当时间戳，轮询 `ZRANGEBYSCORE` 的问题？（空轮询、集群单点、重复消费要自己做）  
- 为什么生产禁用 `KEYS`？（阻塞。用 `SCAN`）

## Q3: 过期与淘汰

**30 秒答法**  
过期：惰性删除（访问时发现过期）+ 定期抽样删除。不会精确到点全表扫。  
淘汰策略（内存满）：`noeviction` 写失败；`allkeys-lru` / `volatile-lru`；`allkeys-lfu` 等。缓存场景常用 `allkeys-lru` 或 LFU。要有 `maxmemory`，否则用到把机器打满。

**追问**  
- 过期 key 会不会立刻从 RDB/AOF 消失？（取决于持久化时机；从库靠主库的 DEL 传播）  
- 热点 key 过期瞬间？（见缓存击穿）

## Q4: 持久化：RDB 与 AOF

**30 秒答法**  
RDB：fork + COW 生成快照，恢复快，丢 fork 之后的数据。  
AOF：写命令日志，`always`/`everysec`/`no`。rewrite 控制文件膨胀。  
生产常见：RDB + AOF 混合（4.0+），`everysec` 平衡。不能把 Redis 当唯一真相库，除非业务接受丢秒级数据并经过完整容灾设计。

**追问**  
- fork 导致的延迟？（大内存 COW、瞬间 RSS 涨，子进程写盘拖慢）  
- AOF 刷盘失败怎么办？（看配置，可能忽略或拒绝写）  
- 主从全量 vs 增量？（PSYNC；复制积压缓冲区不够会全量）

## Q5: 缓存穿透、击穿、雪崩

**30 秒答法**

| 问题 | 含义 | 常用手段 |
|------|------|----------|
| 穿透 | 查不存在的数据，打到 DB | 空值短 TTL、布隆/布谷鸟过滤器、参数校验 |
| 击穿 | 热点 key 过期 | 互斥重建（单飞）、逻辑过期、永不过期 + 异步刷新 |
| 雪崩 | 大量 key 同时过期或 Redis 挂 | TTL 加随机、副本/集群、熔断降级、本地缓存 |

**追问**  
- 布隆过滤器误判怎么办？（只能「可能存在」，不存在是准的；误判会放过到 DB，要可接受）  
- Redis 挂了还有本地缓存 Caffeine？（多级缓存一致性更难，要讲清过期与最大体积）

## Q6: 分布式锁

**30 秒答法**  
`SET key member NX EX ttl`：原子加锁带过期。value 用唯一 token，释放用 Lua 比较再删，避免删别人的锁。  
问题：业务超时锁过期 → 两个实例同时进临界区。Redisson 看门狗续期能缓解，**不能解决持锁线程 GC/STW 过久或任务实际没做完**。主从异步复制时主宕机，从升主没有锁 → 双主持锁。Redis 锁适合**效率型互斥**（防重复提交、削峰），不适合**正确性要求极高**的资金账（用 DB 唯一约束或 ZK/etcd 的共识锁，并仍要幂等）。

**追问**  
- Redlock 的争议？（依赖多独立节点时钟与失败模式，很多团队不用，宁可用 DB 约束）  
- 可重入怎么做？（value 里记重入次数，仍是同一 token）  
- 锁粒度？（锁用户而不是锁全表）

## Q7: 集群、哨兵、分片

**30 秒答法**  
哨兵：主从 + 故障转移，写在单主，读可从，容量受单机内存限制。  
Cluster：16384 slot，分片扩容，`MOVED`/`ASK`。跨 slot 事务/Lua 受限。  
业务上：先垂直拆 key、再考虑集群。客户端要理解槽位迁移时的重试。

**追问**  
- 热点 slot 怎么办？（拆 key、本地缓存、把热数据独立实例）  
- 为什么 Cluster 不用一致性哈希？（slot 是预分片，迁移以 slot 为单位）

## Q8: 大 key / 热 key / 阻塞命令

**30 秒答法**  
大 key：单个 string 很大，或 hash/zset 元素极多。危害：网络打满、集群迁移卡、过期删除阻塞。治理：拆、压缩、扫描删（`UNLINK`/`HSCAN`）。  
热 key：单 key QPS 打满网卡或 CPU。治理：本地缓存、复制多副本随机前缀、业务削峰。  
排查：`redis-cli --bigkeys`、监控瞬时命中、延迟探针。

**踩坑**  
在 Redis 里存几 MB 的 Java 序列化对象；用 `KEYS *` 当管理后台搜索；把 Redis 当消息总线还要求不丢。
