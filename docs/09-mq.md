# 消息队列

> 面试权重：高频（简历写了 Kafka/RocketMQ 就必挖可靠性）  
> 适合层级：中级及以上

## Q1: 为什么要用 MQ？什么时候不要用？

**30 秒答法**  
三个正当理由：解耦、异步、削峰。不正当理由：觉得微服务之间「应该」都走消息。  
不要用：需要同步强一致结果给用户（下单立刻要库存确认）、查询类、团队没有消费失败治理能力。MQ 引入的是**最终一致性、重复、乱序、积压、运维**，不是免费午餐。

**追问**  
- 和 RPC 怎么选？（要对方结果且短超时 → RPC；允许事后处理 → MQ）  
- 削峰如果消费者永远追不上？（降级、丢弃策略、扩容、把高峰业务改成预扣）

## Q2: Kafka vs RocketMQ vs RabbitMQ（对比题）

**30 秒答法**  
按「模型、吞吐、运维、功能」比，不要背市场份额。

| | Kafka | RocketMQ | RabbitMQ |
|--|-------|----------|----------|
| 模型 | 分区日志，消费者拉 | 队列/Topic + 队列，拉为主 | Broker 推，路由灵活 |
| 吞吐 | 极高，顺序在分区内 | 高，业务向功能多 | 中，延迟可以很低 |
| 顺序 | 单分区 | 顺序消息有专门设计 | 单队列 |
| 延迟/事务消息 | 事务/幂等有，业务事务消息不如 RMQ 顺手 | 事务消息是长项 | 插件/确认机制 |
| 典型 | 日志、大数据、事件流 | 订单、电商业务消息 | 任务、路由复杂的老系统 |

国内业务系统常 RocketMQ；数据管道/日志常 Kafka。说「我们选 X 因为团队已有集群和监控」是加分，不是减分。

## Q3: 怎么保证「不丢」？（分三段讲）

**30 秒答法**  
丢消息发生在三段：**生产、Broker、消费。**

1. **生产：** 同步确认（Kafka `acks=all` + 足够 ISR；RocketMQ 同步发送）。失败重试。不要 fire-and-forget。  
2. **Broker：** 多副本、刷盘策略、机架隔离。接受「同步刷盘换吞吐」。  
3. **消费：** 先处理再提交 offset/ack。处理失败不要提交。要幂等，因为「至少一次」会重复。

没有银弹做到「恰好一次」跨系统业务：Kafka 事务 + 幂等生产者解决的是**管道内**，数据库和下游还要自己幂等。

**追问**  
- `acks=all` 和 `min.insync.replicas` 的关系？（ISR 不够会写失败，这是正确的失败）  
- 消费后先提交再处理会怎样？（崩溃即丢）  
- 自动提交的坑？（批量里部分失败也提交）

## Q4: 重复消费与幂等

**30 秒答法**  
MQ 默认按至少一次设计。幂等手段：业务唯一键（订单号）、数据库唯一约束、状态机（已支付不能再支付）、Redis SET NX（注意过期与 Redis 可靠性）。  
消费端「去重表」要有 TTL 或按业务键落库。不要只靠「我觉得这消息只发一次」。

**追问**  
- 窗口外的重复？（去重 key 过期后又来一条）要用业务状态，不只是 Redis。  
- 更新类操作怎么幂等？（版本号 / 条件更新 `WHERE status=INIT`）

## Q5: 顺序消息

**30 秒答法**  
全局顺序极贵。业务要的通常是**同一对象的局部顺序**（同一订单号进同一分区/队列）。Kafka：相同 key。RocketMQ：顺序消息用 hash 到同一队列。  
代价：单分区并发变成 1，热点 key 会成为瓶颈。乱序容忍的业务不要开顺序。

**追问**  
- 分区扩容后 key 的映射变了怎么办？（旧数据期间不能随便加分区，或接受短暂乱序）  
- 消费失败卡住整个分区？（是。顺序消费失败要有停写/死信策略，否则队头阻塞）

## Q6: 积压怎么处理？

**30 秒答法**  
先看：是生产暴涨、消费变慢、还是挂了。  
应急：扩消费者（分区数要够）、跳过坏消息进死信、临时丢弃可丢的日志类、暂停非核心生产。  
根治：消费逻辑优化、批量、避免每次打慢 SQL、分区数预留、限流生产。  
面试准备一组数字：平时 lag、报警阈值、最大追赶速率。

**追问**  
- Kafka 消费者数大于分区数？（多出来的闲着）  
- 积压时能改分区数救急？（能加分区，但 key 顺序可能打乱）

## Q7: 事务消息 / 本地消息表 / Outbox

**30 秒答法**  
业务要「库成功则一定发出消息」：  
- **本地消息表 / Outbox：** 同一数据库事务写业务行 + 消息行，job 扫描发出。最朴素最稳。  
- **RocketMQ 事务消息：** half 消息 + 回查。要理解回查接口必须能根据业务键判断成败。  
不要「先发消息再写库」还声称有事务。

## Q8: 延迟消息与死信

**30 秒答法**  
延迟：RocketMQ 有内置延迟级别；Kafka 常用时间轮/暂停消费/独立延迟 topic。死信：超过重试次数进入 DLQ，必须有人处理或报警，否则等于丢。重试要指数退避，毒消息不要无限打爆下游。
