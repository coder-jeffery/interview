# 计算机网络

> 面试权重：必会（校招更爱问；社招结合 HTTPS、超时、连接池）  
> 适合层级：所有人

## Q1: TCP 三次握手、四次挥手

**30 秒答法**  
握手：SYN → SYN+ACK → ACK。目的是双方确认初始序号、避免已过期 SYN 打开连接。  
挥手：FIN → ACK → FIN → ACK。半关闭：一边不再写，仍可读。`TIME_WAIT` 在主动关闭方，等 2MSL，为了丢弃迟到报文、让对方的 ACK 可重传。

**追问**  
- 为什么不是两次握手？（第三次才让客户端确认「我的序号被对端接受」，防旧 SYN）  
- 大量 `TIME_WAIT` 怎么办？（短连接过多；调 `tcp_tw_reuse` 要懂风险；更应改连接复用/HTTP 长连接）  
- `CLOSE_WAIT`？（本端没收/不发 FIN，应用没关 socket）  
- SYN 洪水？（半连接队列；`syncookies`）

## Q2: TCP 可靠、滑动窗口、拥塞控制（点到即可）

**30 秒答法**  
可靠：序号、确认、重传、校验。流量控制：接收窗口。拥塞：慢启动、拥塞避免、快重传快恢复。面试社招不需要背每一个 RFC 名字，要能连到：**带宽时延积、超时重传导致 RT 毛刺、连接池比反复握手更重要。**

**追问**  
- 粘包/拆包？（TCP 是流。应用层定长、分隔符、或长度头。HTTP/1.1 用 Content-Length/chunked）  
- UDP 什么时候用？（DNS、实时音视频、QUIC 的底。自己做可靠等于再造 TCP）

## Q3: HTTP/1.1 vs HTTP/2 vs HTTP/3

**30 秒答法**  
1.1：文本、队头阻塞（一连接一请求流水线几乎不用）、Keep-Alive。  
2：二进制帧、多路复用、HPACK、服务端推送（实际用得少）。仍跑在 TCP 上，**TCP 层队头阻塞**还在。  
3：QUIC on UDP，握手更快（常 1-RTT / 0-RTT）、连接迁移（换网），解决 TCP 队头阻塞。

**追问**  
- 浏览器对 1.1 为什么开 6 个连接？（队头阻塞的历史妥协）  
- gRPC 为什么绑 HTTP/2？（流、多路复用、protobuf）  
- 0-RTT 的安全代价？（重放，要业务幂等）

## Q4: HTTPS / TLS

**30 秒答法**  
TLS 提供加密、完整性、身份（证书）。握手：协商版本与套件、证书校验、密钥交换（现代主流 ECDHE，前向保密），再切对称加密传数据。证书链要信任 CA。双向 TLS 在服务间网格常见。

**追问**  
- 对称 vs 非对称？（非对称只用于握手/签名，数据走 AES 等）  
- 证书过期事故？（监控到期、自动化签发）  
- 中间人怎么防？（校验证书主机名与链，不要关校验图省事）

## Q5: 从输入 URL 到页面（压缩成后端视角）

**30 秒答法**  
DNS → TCP/TLS → HTTP 请求 → 负载均衡/网关 → 服务 → DB/缓存 → 响应。后端要能插入：DNS TTL、LB 四层 vs 七层、Keep-Alive、超时从哪一层设（客户端、网关、服务、DB）。

**追问**  
- DNS 缓存层级？（浏览器、OS、本地、权威）  
- 301/302/304？（永久/临时重定向；缓存校验）  
- Cookie vs Token？（Cookie 可 HttpOnly；Token 常放 Authorization；CSRF 与 Cookie 自动带有关）

## Q6: 后端超时与连接池（社招高频）

**30 秒答法**  
超时必须**由外到内递减**：用户 3s，网关 2s，服务调下游 1s，DB 更短。否则网关还在等，服务已经自己超时重试，放大故障。  
HTTP 客户端连接池：最大连接、每路由连接、空闲淘汰。池太小排队，太大把下游打满。面试能讲你项目里的具体数字和一次「超时叠加重试雪崩」。

**踩坑**  
默认无限超时；重试打在写请求上且下游不幂等；DNS 变更后连接池仍连老 IP。
