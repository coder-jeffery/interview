# MySQL

> 面试权重：必会（往往比 Java 语法更能决定通过）  
> 适合层级：所有人（中高级挖到锁和 MVCC）

## Q1: 为什么 InnoDB 是默认引擎？

**30 秒答法**  
InnoDB：事务、行锁、MVCC、崩溃恢复（redo/undo）、外键（可关）、聚簇索引。MyISAM：表锁、不支持事务，现在几乎只在历史题里出现。面试默认 InnoDB。

**追问**  
- 表存在哪个文件？（`.ibd` 独立表空间常见；系统表空间历史包袱）  
- redo 和 binlog 的区别？（redo 是 InnoDB 崩溃恢复；binlog 是 Server 层复制/备份，两阶段提交保证一致）

## Q2: 索引：B+Tree、聚簇、最左前缀、覆盖索引

**30 秒答法**  
InnoDB 索引是 B+Tree：叶子在同一层、双向链表，范围扫友好；非叶只有键和指针，扇出大、树矮。  
主键是聚簇索引，叶子是整行。二级索引叶子是「键 + 主键」，回表再用主键找行。覆盖索引：查询列都在索引里，不回表。  
最左前缀：`(a,b,c)` 能用 `a`、`a,b`、`a,b,c`；`b,c` 用不上（除非索引跳跃扫描等特殊优化，别当默认）。范围条件会截断后面的列（`a=? AND b>1 AND c=?` 里 c 往往用不上排序/过滤的索引能力）。

**追问**  
- 为什么不建议用 UUID 当主键？（随机插入页分裂、二级索引更胖）  
- 联合索引列顺序怎么定？（区分度高且等值查询在前，还要看排序与覆盖）  
- 索引下推 ICP？（存储引擎先按索引条件过滤，少回表）  
- 函数包列为什么失效？（`DATE(col)` 用不上普通索引，要用函数索引或改写）

**踩坑**  
隐式类型转换、字符集不一致、`OR`、前导模糊 `%abc` 都会让索引失效或变差。用 `EXPLAIN`，不要猜。

## Q3: 事务隔离级别与 MVCC

**30 秒答法**  
四种隔离：读未提交、读已提交（RC）、可重复读（RR，InnoDB 默认）、串行化。脏读/不可重复读/幻读是对应现象。  
InnoDB RR 用 MVCC + next-key 锁：快照读（普通 SELECT）看 Read View，当前读（`FOR UPDATE` / `LOCK IN SHARE MODE` / 更新删除）加锁。  
MVCC：undo 链上的历史版本。Read View 记录活跃事务 ID，决定行版本可见性。RR 的 Read View 在事务第一次快照读时建；RC 每条语句建一次——所以 RC 不可重复读，RR 可重复。

**追问**  
- RR 能完全避免幻读吗？（快照读可以「看起来」没有；当前读靠间隙锁。面试说清楚这两种读）  
- 长事务的害？（undo 不能清、历史版本长、锁与主从延迟）  
- `SELECT ... FOR UPDATE` 在 RR 下锁什么？（符合条件的行 + 间隙，防幻）

## Q4: 锁：行锁、间隙锁、临键锁、意向锁

**30 秒答法**  
InnoDB 锁在索引上。没有合适索引会退化成很多行锁甚至表级效果。  
- 记录锁：锁住索引记录  
- 间隙锁：锁记录之间的间隙，防插入（RR）  
- 临键锁：记录 + 左边间隙  
- 意向锁：表级，为了和表锁快速冲突检测  

RC 下基本没有间隙锁（有例外），所以幻读窗口更大、死锁有时更少，互联网公司常用 RC。

**追问**  
- 死锁怎么处理？（InnoDB 回滚代价小的那个事务；应用要重试。排查 `SHOW ENGINE INNODB STATUS` 或 error log）  
- 如何减少死锁？（固定更新顺序、索引精确、缩短事务、RC）  
- 插入意向锁？（插入到间隙前的一种等待，多个插入同一间隙会互相等）

## Q5: 一条更新 SQL 经过什么？两阶段提交

**30 秒答法（口述一条链）**  
客户端 → Server 解析优化 → InnoDB：加锁、改内存页、写 undo、写 redo（prepare）→ 写 binlog → redo commit。崩溃恢复靠 redo 与 binlog 的 2PC，避免「库有数据但从库没有」或反过来。  
`innodb_flush_log_at_trx_commit` 和 `sync_binlog` 控制持久化强度：都为 1 最安全最慢；双 1 是金融默认，互联网常做权衡。

**追问**  
- redo 是物理日志、binlog 是逻辑日志，这个说法准确吗？（大致对：redo 页级物理/生理；binlog 有 statement/row/mixed，现多用 row）  
- 主从延迟原因？（大事务、从库单线程 SQL 线程历史问题、磁盘、网络；并行复制要讲你用的版本）

## Q6: 慢 SQL 怎么优化（要有步骤）

**30 秒答法**  
1. 确认慢：`slow_query_log`、APM、`performance_schema`  
2. `EXPLAIN` / `EXPLAIN ANALYZE`：type、key、rows、Extra（Using filesort / temporary）  
3. 有没有合适索引、是否回表过多、是否隐式转换  
4. 改写 SQL：避免 `SELECT *`、分页深翻（延迟关联 / 记上次最大 ID）、`COUNT(*)` 大表用近似或汇总表  
5. 还慢再谈：覆盖索引、拆查询、缓存、归档、分库分表

**追问**  
- `LIMIT 1000000, 10` 为什么慢？（扫过 1000000 行）  
- 最左前缀和 `ORDER BY` 怎么配合才能免 filesort？  
- 执行计划不准？（统计信息过期 `ANALYZE TABLE`；直方图）

## Q7: 分库分表什么时候才做？

**30 秒答法**  
先垂直拆（模块拆库）、缓存、读写分离、归档。单表亿级且确实成为瓶颈再水平拆。代价：跨库事务、跨页查询、二次排序、扩容迁移。分片键要选**几乎所有请求都带的维度**（用户 ID），避免「按用户拆了还要按订单时间全扫」。

**追问**  
- 非分片键查询怎么办？（ES / 宽表 / 数据服务，而不是每个维度都拆一套）  
- 全局 ID？（号段、Snowflake，不要自增主键跨库）  
- 扩容？（2 的幂、一致性哈希、双写迁移）
